# H.E.X. engineering execution guide

Status: reusable workflow, updated October 11, 2026; the latest user request determines the active task.

Improve a concrete part of H.E.X. play or maintenance with a bounded, verified
change. Readable decisions, responsive controls, useful elemental choices and
original artwork matter more than additional systems, files or assertion totals.

## Start from current authority

Read the [resume](HEX-RESUME.md), the current authorized task in the
[implementation record](OVERHAUL-IMPLEMENTATION.md), then relevant
[specification](../SPECIFICATION.md) and source. A closed batch is not permission
to begin another. The resume owns exact build/package identities and acceptance;
historical evidence qualifies only its recorded source.

Confirm the actual checkout, dirty boundary and protected runnable build.
Current scope is Windows, 120 Hz, six ingredients, 63 compositions across eight
deliveries (504 spells), twelve positions, thirty profiles, twenty-one ancestries,
63 bounded chemistry outcomes and an eight-player cap. Do not derive current
scope from retired role cards or old catalog tables.

## Assign and implement bounded work

Use the [dispatch contract](ASPECT-DELEGATION.md): at most three specialists plus
root, disjoint write paths and independent review. Shared code has one writer.
Root owns integration and serializes all Godot imports/tests/captures/profiles/
exports. Do not launch engines against changing source.

- Preserve paid resources/matter, input ownership, deterministic contact order,
  exact whole-hex membership, height/protection, timings and strict same-build
  networking. Refusal cannot silently spend on another choice.
- Optimize measured repeated work with conservative math, immutable sharing and
  bounded caches whose invalidation and fallback are tested. Do not hide costs
  by weakening validation, skipping accepted state or lowering gameplay cadence.
- Measure meaningful paid/empty/dense/cover cases and distinguish warm cost,
  setup, p95/p99/cold tails, memory and full-path behavior. A fast kernel does
  not establish a faster game or better physical input feel.
- Keep original pixels registered, travel independent of aim and threat cues
  faithful to actual state. Held poses are not complete animation cycles.
- Use primary sources for unfamiliar techniques. Distinguish a game's documented
  mechanism, author intent and measured outcome from the H.E.X. adaptation.

## Verification and handoff

Start with a reproducible control and meaningful positive/adversarial regressions.
For documentation changes, run the source-only scope/link checks before expensive
gates; every top-level `docs/*.md` needs an explicit `Status:` in its first ten
lines. Preserve the historical checkpoint summary when checking
`scripts/current-build-summary.ps1 -CheckPath README.md`.

After a focused change, inspect the diff and qualify the affected scope. At an
integrated production freeze run Full/import/identity/boot and applicable
actual-input, native, network or exported-byte gates. Repeat testing only when
changed source or unresolved risk justifies it. Keep failed receipts; never
rename an interrupted or partial run into a Full pass.

Separate code correctness, rendered pixels, animation feel, audio, balance,
package/install, localhost and physical Internet acceptance. Dense sustained
performance requires representative measurements. Report exact changed paths,
checks executed, NOT_RUN checks and practical limits.

Keep one contract, one implementation record and a concise handoff. Archive
needed old narrative before replacing it. Preserve user changes, original
assets, personal saves, independent test oracles and working fallbacks. Delete
only reviewed obsolete material within the authorized scope, and do not edit
personal memory without an explicit user request.
